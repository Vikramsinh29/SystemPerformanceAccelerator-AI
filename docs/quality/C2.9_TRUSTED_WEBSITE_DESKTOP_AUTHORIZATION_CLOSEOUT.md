The C2.9 objective was to establish and verify a trusted website-to-Windows-desktop commercial authorization path for PC-SPA without reintroducing historical beta activation behavior.

## Verified authorization flow

The verified flow is:

1. Authenticated PC-SPA website session.
2. Server resolves trusted account identity.
3. Server owns the `pcspa-pro` product identity.
4. Licensing backend issues a random, short-lived, one-time installation authorization code.
5. Only the SHA-256 hash of the code is stored server-side.
6. Browser launches the registered `pcspa://authorize` Windows protocol.
7. Desktop receives the authorization code.
8. Desktop exchanges the code through the production licensing endpoint.
9. Backend atomically consumes the authorization.
10. Desktop stores only the returned Bearer credential and expiry.
11. Credential storage uses Windows DPAPI under the current user context.

Browser or desktop supplied account/product identity is not trusted.

## Storage policy note

For Microsoft Store/MSIX distribution, package-private redirected LocalAppData is accepted as the current commercial credential location.

A future direct installer may resolve ordinary LocalAppData differently. Credential sharing or migration between Store and direct-install channels must be an explicit product decision and is not required for C2.9 closure.

## Residual security note

The custom `pcspa://` protocol uses a short-lived one-time authorization code and therefore limits the impact of URI interception. The authorization code is not itself a durable credential.

No stronger Windows protocol ownership mechanism is claimed by C2.9.

## Closeout decision

C2.9 trusted website-to-desktop authorization is considered **verified and complete**.

The next commercial-release work may proceed without reopening C2.9 unless a future distribution-channel, account-linking, protocol-registration, or credential-storage requirement materially changes the verified design.
